I Implemented the Protocol Behind AgentCore Payments — Here's What the Managed Service Hides

#AWS#AgentCore#Agentic AI#x402

AWS previewed a capability that lets AI agents spend money on their own. The demos look magical. So I rebuilt the protocol underneath it from scratch — real cryptographic signing, a budget guard, a runaway-spend experiment — to find out what you actually sign up for when you “connect a wallet.” The code is on GitHub; every number below comes from running it.

(Views are my own. AgentCore Payments is in preview as of May 2026; APIs may change. My implementation models the open x402 protocol it uses — signing is real, settlement is mocked. No real funds move.)

The line we just crossed

For years, agents could read, think, talk, and call APIs. The one thing they couldn’t do was spend money. On May 11, 2026, AWS previewed Amazon Bedrock AgentCore Payments: built with Coinbase and Stripe, it lets an agent autonomously pay for APIs, MCP servers, web content, and other agents.

The marketing is “connect a Coinbase CDP or Stripe Privy wallet, set a spending limit, and your agent transacts on its own.” That sentence hides a lot. I wanted to see what’s under it, so I implemented the protocol it runs on — x402 — myself. Not to replace AWS, but to make the governance questions executable instead of hand-wavy.

What I built is small enough to read in one sitting: a merchant that speaks HTTP 402, an agent wallet that signs payments with real Ed25519 keys, a PaymentSession budget guard, and an experiment that runs a runaway agent loop with and without the guard. Seven tests, all passing. Let me walk through what I learned.

Part 1 — What a payment actually is

The microtransaction problem (why not just use a credit card)

An agent buying one API call or one snippet of data is usually paying fractions of a cent. Credit cards have minimum fees that make a $0.003 charge absurd, plus geographic limits. So “agent pays small change on demand” was economically impossible on card rails. x402 solves it with stablecoins over an open protocol.

x402 in three steps

x402 (an open standard from Coinbase) reuses the HTTP 402 Payment Required status code — reserved since the early web, basically unused for 30 years. The flow:

1. Agent requests a paid resource → server replies 402 + payment requirements
2. Agent signs the requirements with its wallet key → a payment proof
3. Agent retries with the proof → server verifies → 200 + data

Here’s my merchant returning a 402. Notice the nonce — it’s what stops a captured proof from being replayed:

def _make_requirements(self) -> dict:
    return {
        "scheme": "exact",
        "amount": "0.001",
        "currency": "USDC",
        "pay_to": MERCHANT_ADDRESS,
        "resource": "/v1/market-data",
        "nonce": secrets.token_hex(8),   # fresh per challenge → no replay
    }

The part the managed service hides: what the agent signs

“Connect a wallet” makes the signing invisible. But the signature is the security artifact. When my agent pays, it signs exactly this payload with an Ed25519 key:

def sign_payment(self, requirements: dict) -> dict:
    payload = {
        "scheme":   requirements["scheme"],
        "amount":   requirements["amount"],
        "currency": requirements["currency"],
        "pay_to":   requirements["pay_to"],
        "resource": requirements["resource"],
        "nonce":    requirements["nonce"],
        "from":     self.address,
    }
    sig = self._sk.sign(canonical(payload))
    return {"payload": payload, "signature": _b64(sig), "public_key": self.public_key_b64}

That signature is a non-repudiable authorization: this wallet agreed to pay this amount to this recipient for this resource at this moment. When you let an agent “transact autonomously,” this is what it’s authorizing on your behalf, thousands of times, with no human in the loop. Sit with that for a second.

And it’s tamper-evident. Sign a payload, then try to lower the amount before sending — verification fails:

verify (untampered):     True
verify (amount tampered): False

That’s a real test in the repo (test_signature_tampering_rejected), not a diagram.

What AWS wraps around this

In AgentCore you don’t write any of the above. Each piece I hand-built maps to a managed component:

That’s the honest trade: AgentCore saves you weeks of exactly the work in that middle column. But it also means the budget guard, the TTL, the audit trail — the parts that contain failure — are now configuration you must get right, not code you wrote and understand. Convenience moves the risk, it doesn’t remove it. Which is exactly why the next part matters.

Part 2 — The experiment: what a runaway agent costs

Agents are non-deterministic. They get stuck in loops; they get prompt-injected. So the question isn’t “does payment work” — it’s “when it goes wrong, how bad is it?” I ran the same buggy agent, stuck in a 100-call loop against a $0.001 endpoint, two ways.

Without a budget guard

for _ in range(100):
    call_paid_api(merchant, wallet, session=None)   # PAYG: no ceiling

Result: 100 payments, all of them. $0.10 spent, nothing stops it. At $0.001 that’s pocket change — but the loop is the point, not the unit price. Which brings us to throughput.

”A human will catch it” is not a control

I measured how fast the full handshake runs (challenge → Ed25519 sign → verify):

3,497 payments/sec on an M-series laptop
= $209.79 / minute of autonomous spend at $0.001/call

A human cannot react to that. By the time you’ve read this paragraph, an unguarded loop has spent more than your coffee. “We’ll monitor it” is not a safety mechanism when the agent transacts 3,500 times a second.

With a budget guard

The guard sits between getting the 402 and signing it — it’s the entire governance lever:

if session is not None:
    reserved = session.authorize(amount)   # raises BudgetExceeded → payment never signed

Same 100-call loop, $0.05 ceiling:

ModePaymentsSpentStopped at
No guard100 / 100$0.100never
Budget guard ($0.05)50$0.050call #51

The finding I didn’t expect: budget alone isn’t enough

I added a third run — a $999 budget (effectively unlimited) but a session that expires after 20 attempts:

ModePaymentsStopped at
TTL guard ($999 budget, 20-attempt TTL)20call #21, on time

A slow-drip agent that stays under any single budget can still run forever. Money caps the amount; only a TTL caps the duration. You need both — which is exactly why AgentCore’s PaymentSession has both maxSpendAmount and an expiry. Now I know why, because I watched the failure mode the expiry exists to prevent.

The edge case AWS documents — and why it bites

AWS’s docs note: if signing fails after a budget deduction, the budget isn’t charged. Sounds like a footnote. It isn’t. Without that refund, every transient failure permanently burns budget, and a flaky endpoint slowly starves your agent. My guard implements it; a test proves spend stays exact across a mid-flight failure:

5 attempts, 1 fails after reservation → charged for 4, not 5 ✓

Part 3 — What this means for the enterprise

Here’s the shift, stated plainly: cloud spend used to be human-approved budgets consumed by human-built systems. AgentCore Payments removes the human from the loop. The agent decides and spends, mid-execution, 3,500 times a second.

That changes three things at once:

  1. FinOps stops being forecasting and becomes real-time control. “How much will this cost this month” is no longer a number you can predict; it’s a ceiling you have to enforce.
  2. Security gains a money dimension. A prompt-injected agent no longer just leaks data — it spends. The signature I showed in Part 1 is what an attacker would be inducing your agent to produce.
  3. Governance has to answer “who decided to spend this?” with “the AI did, under these limits, and here’s the audit trail.” If you can’t produce the limits and the trail, you’re not ready.

The gap is the opportunity. Most organizations haven’t productionized an agent that talks, yet the infrastructure already lets agents spend. The consultants and architects who can answer “how do we do this under control” — with executable answers, not slideware — are the ones who’ll be trusted with it.

The distance between the two is concrete. Here’s what separates a payment demo from something you’d run on a real budget:

PoC / demo

"It pays. Ship it."

  • One wallet, one agent, no separation
  • A budget that's set but never tested for actual denial
  • No TTL — relies on the loop ending on its own
  • Logs to stdout; no spend-to-intent linkage
  • "We'll watch the dashboard" as the kill switch
  • Reaches all 10,000 Bazaar endpoints
Production

"It pays, under control, provably."

  • Per-agent wallets; hot/cold split; rotation
  • Budget + cumulative cap, with a test that proves denial fires
  • Session TTL bounds time, not just amount
  • CloudWatch + X-Ray, each spend tied to a triggering intent
  • A real kill switch, drilled — not a human watching a graph
  • Merchant allowlist, not the whole Bazaar

Every item on the right maps to a failure I either measured in x402-lab or had to design around. None of it is exotic — it’s just the work that “connect a wallet” quietly defers to you.

Closing

AWS gave agents a wallet, and the protocol underneath is genuinely elegant. But “connect a wallet and set a limit” compresses a non-repudiable signing authority, a 3,500/sec spend rate, and a two-dimensional containment problem into one sentence. The right move isn’t to fear it — it’s to turn payments on only after you’ve designed, and tested, the guard.

The agent economy has started. The question was never “can we.” It’s “can we do it under control” — and that’s an engineering question with a measurable answer.
