AgentCore Payments의 프로토콜을 직접 구현해봤다 — 관리형 서비스가 감추는 것

#AWS#AgentCore#Agentic AI#x402

AWS가 AI 에이전트에게 스스로 돈을 쓰게 하는 기능을 내놨다. 데모는 마법 같다. 그래서 나는 그 밑의 프로토콜을 직접 구현했다 — 실제 암호학적 서명, 예산 가드, 폭주 시뮬레이션. “지갑을 연결하라”가 실제로 무엇을 약속하는 건지 보려고. 코드는 GitHub에 있고, 아래 모든 숫자는 그걸 실제로 돌려서 나온 값이다.

(개인 의견. AgentCore Payments는 2026년 5월 기준 preview이며 API는 변경될 수 있다. 내 구현은 이 서비스가 쓰는 개방형 x402 프로토콜을 모델링한 것 — 서명은 실제, settlement는 mock이다. 실제 자금은 움직이지 않는다.)

우리가 방금 넘은 선

지난 몇 년간 에이전트는 읽고, 생각하고, 말하고, API를 호출했다. 단 하나 못 한 게 돈을 쓰는 것이었다. 2026년 5월 11일, AWS는 Amazon Bedrock AgentCore Payments를 preview로 공개했다. Coinbase·Stripe와 함께 만든 이 기능은 에이전트가 API, MCP 서버, 웹 콘텐츠, 다른 에이전트에게 자율적으로 결제하게 한다.

마케팅 문구는 “Coinbase CDP 또는 Stripe Privy 지갑을 연결하고, 한도를 설정하면, 에이전트가 알아서 거래한다”이다. 이 한 문장이 꽤 많은 걸 감춘다. 그 아래가 궁금해서, 이 서비스가 돌리는 프로토콜인 x402를 직접 구현했다. AWS를 대체하려는 게 아니라, 거버넌스 질문을 말이 아니라 실행 가능한 것으로 만들기 위해서.

만든 것은 한자리에서 다 읽을 만큼 작다: HTTP 402를 말하는 머천트, 실제 Ed25519 키로 결제에 서명하는 에이전트 지갑, PaymentSession 예산 가드, 그리고 가드가 있을 때와 없을 때 폭주하는 에이전트 루프를 돌리는 실험. 테스트 7개, 전부 통과. 무엇을 배웠는지 풀어본다.

Part 1 — 결제란 실제로 무엇인가

마이크로트랜잭션 문제 (왜 카드로는 안 되나)

에이전트가 사는 API 한 건, 데이터 한 조각은 보통 1센트의 분수다. 신용카드는 최소 수수료가 있어 0.003달러 결제가 말이 안 되고, 지역 제약도 크다. 그래서 “에이전트가 필요할 때마다 잔돈을 낸다”는 카드로는 경제적으로 불가능했다. x402는 이걸 스테이블코인 + 개방형 프로토콜로 푼다.

x402, 세 단계

x402(Coinbase의 개방형 표준)는 HTTP 402 Payment Required 상태 코드를 재활용한다 — 초창기 웹부터 예약돼 있었지만 30년간 거의 안 쓰인 코드다. 흐름은:

1. 에이전트가 유료 리소스 요청 → 서버가 402 + 결제 요건 응답
2. 에이전트가 지갑 키로 요건에 서명 → 결제 증명(proof)
3. proof 붙여 재요청 → 서버 검증 → 200 + 데이터

내 머천트가 402를 반환하는 부분이다. nonce를 주목하라 — 캡처한 proof를 재사용(replay)하지 못하게 막는 장치다:

def _make_requirements(self) -> dict:
    return {
        "scheme": "exact",
        "amount": "0.001",
        "currency": "USDC",
        "pay_to": MERCHANT_ADDRESS,
        "resource": "/v1/market-data",
        "nonce": secrets.token_hex(8),   # 챌린지마다 새로 → replay 차단
    }

관리형 서비스가 감추는 것: 에이전트가 무엇에 서명하는가

“지갑을 연결하라”는 서명을 보이지 않게 만든다. 하지만 서명이야말로 보안의 핵심이다. 내 에이전트가 결제할 때, Ed25519 키로 정확히 이 payload에 서명한다:

def sign_payment(self, requirements: dict) -> dict:
    payload = {
        "scheme":   requirements["scheme"],
        "amount":   requirements["amount"],
        "currency": requirements["currency"],
        "pay_to":   requirements["pay_to"],
        "resource": requirements["resource"],
        "nonce":    requirements["nonce"],
        "from":     self.address,
    }
    sig = self._sk.sign(canonical(payload))
    return {"payload": payload, "signature": _b64(sig), "public_key": self.public_key_b64}

이 서명은 부인 불가능한 승인이다: 이 지갑이, 이 금액을, 이 수신자에게, 이 리소스를 위해, 이 순간에 지불하기로 동의했다. 에이전트를 “자율적으로 거래”하게 둔다는 건, 사람 개입 없이 수천 번 당신을 대신해 이걸 승인하게 둔다는 뜻이다. 잠깐 곱씹어볼 만하다.

게다가 변조가 드러난다. payload에 서명한 뒤, 보내기 전에 금액을 낮춰보면 검증이 실패한다:

verify (변조 안 함):   True
verify (금액 변조):    False

repo의 실제 테스트(test_signature_tampering_rejected)다. 다이어그램이 아니라.

AWS가 이 위에 감싸는 것

AgentCore에서는 위 코드를 한 줄도 안 쓴다. 내가 직접 만든 각 조각이 관리형 구성요소로 이렇게 매핑된다:

관심사내가 직접 구현 (x402-lab)AgentCore 대응
지갑 키wallet.py — 메모리상 Ed25519 키AgentCore Identity (PaymentCredentialProvider)
유료 엔드포인트 접근하드코딩된 머천트 URLAgentCore Gateway + x402 Bazaar (1만+ 엔드포인트)
페이월 사이트미구현AgentCore Browser
예산 + 만료budget_guard.py — 내가 쓴 PaymentSessionPaymentSession (maxSpendAmount, TTL)
감사 추적print() + results.jsonCloudWatch vended logs + X-Ray spans

정직한 거래다. AgentCore는 가운데 열의 작업 몇 주치를 아껴준다. 하지만 그건 동시에, 실패를 봉쇄하는 부분 — 예산 가드, TTL, 감사 추적 — 이 이제 내가 짜서 이해하는 코드가 아니라, 내가 정확히 설정해야 하는 구성이 됐다는 뜻이다. 편리함은 위험을 옮길 뿐, 없애지 않는다. 다음 부분이 중요한 이유다.

Part 2 — 실험: 폭주하는 에이전트는 얼마를 태우나

에이전트는 비결정적이다. 루프에 빠지고, 프롬프트 인젝션을 당한다. 그래서 질문은 “결제가 되는가”가 아니라 “잘못됐을 때 얼마나 나쁜가”다. 같은 버그 걸린 에이전트를, $0.001 엔드포인트에 100번 호출하는 루프에 넣고, 두 가지 방식으로 돌렸다.

예산 가드가 없을 때

for _ in range(100):
    call_paid_api(merchant, wallet, session=None)   # PAYG: 한도 없음

결과: 100번 전부 결제. $0.10 소진, 아무것도 못 막는다. $0.001이면 푼돈이지만, 핵심은 단가가 아니라 루프다. 그래서 처리량(throughput)을 봐야 한다.

”사람이 보고 막으면 된다”는 통제가 아니다

전체 핸드셰이크(챌린지 → Ed25519 서명 → 검증)가 얼마나 빨리 도는지 측정했다:

M 시리즈 노트북에서 초당 3,497건 결제
= $0.001/건 기준 분당 $209.79 의 자율 지출

사람은 여기에 반응할 수 없다. 이 문단을 읽는 사이에, 가드 없는 루프는 당신 커피값보다 많이 썼다. 에이전트가 초당 3,500번 거래하는데 “모니터링하겠다”는 건 안전장치가 아니다.

예산 가드가 있을 때

가드는 402를 받은 다음, 서명하기 전에 끼어든다 — 이게 거버넌스의 핵심 레버다:

if session is not None:
    reserved = session.authorize(amount)   # BudgetExceeded 발생 → 결제 서명 자체가 안 됨

같은 100번 루프, $0.05 한도:

모드결제소진멈춘 지점
가드 없음100 / 100$0.100안 멈춤
예산 가드 ($0.05)50$0.05051번째 호출

예상 못 한 발견: 예산만으로는 부족하다

세 번째 실험을 추가했다 — $999 예산(사실상 무제한)이지만 20번 시도 후 만료되는 세션:

모드결제멈춘 지점
TTL 가드 ($999 예산, 20회 TTL)2021번째, 시간으로

어떤 단일 예산 밑으로 천천히 흘리는 에이전트는 영원히 돌 수 있다. 돈은 금액을 막고, TTL만이 지속 시간을 막는다. 둘 다 필요하다 — AgentCore의 PaymentSession이 maxSpendAmount와 만료를 둘 다 가진 게 바로 이 이유다. 이제 그 이유를 안다. 만료가 막으려는 실패 모드를 직접 봤으니까.

내 말을 믿지 말고 직접 슬라이더를 움직여보라. 아래는 budget_guard.py와 똑같은 로직을 브라우저에서 돌린다. 예산을 끄면 곡선이 멈추지 않고, TTL을 켜고 예산을 크게 주면 시간이 대신 멈추는 걸 볼 수 있다:

직접 해보기: 폭주는 어디서 멈추나?budget_guard.py와 동일한 로직. 슬라이더를 움직여보라. 곡선은 에이전트의 누적 지출이다.
50 결제 횟수$0.050 총 지출예산으로 차단된 호출 #51

예산이 먼저 물었다: 루프가 아무리 길어도 손실은 한도에서 멈춘다.

AWS가 문서에 적은 엣지 케이스 — 왜 무는가

AWS 문서엔 이런 주석이 있다: 예산 차감 후 서명이 실패하면, 예산은 차감되지 않는다. 각주처럼 보인다. 아니다. 이 환불이 없으면, 일시적 실패가 매번 예산을 영구히 태우고, 불안정한 엔드포인트가 에이전트를 서서히 굶긴다. 내 가드는 이걸 구현했고, 테스트가 중간 실패에도 지출이 정확함을 증명한다:

5번 시도, 1번이 예약 후 실패 → 5가 아닌 4건만 차감 ✓

Part 3 — 엔터프라이즈에 의미하는 것

전환을 분명히 말하면: 클라우드 지출은 원래 사람이 승인한 예산을, 사람이 만든 시스템이 소비하는 구조였다. AgentCore Payments는 사람을 사슬에서 뺀다. 에이전트가 실행 도중, 초당 3,500번, 스스로 판단해 쓴다.

이게 세 가지를 동시에 바꾼다:

  1. FinOps는 예측이 아니라 실시간 통제가 된다. “이번 달에 얼마 쓸까”는 더 이상 예측 가능한 숫자가 아니라, 강제해야 하는 한도다.
  2. 보안에 돈의 차원이 생긴다. 프롬프트 인젝션된 에이전트는 이제 데이터만 새는 게 아니라 돈을 쓴다. Part 1의 그 서명이, 공격자가 당신 에이전트에게 만들게 유도할 바로 그 산출물이다.
  3. 거버넌스는 “누가 이 돈을 쓰기로 했나”에 “AI가, 이 한도 안에서, 그리고 여기 감사 추적이 있다”로 답해야 한다. 한도와 추적을 못 내놓으면, 준비가 안 된 거다.

이 간극이 기회다. 대부분의 조직은 말하는 에이전트도 production화 못 했는데, 인프라는 이미 에이전트가 돈 쓰게 한다. “이걸 통제하면서 어떻게 하나”에 — 슬라이드가 아니라 실행 가능한 답으로 — 대답할 수 있는 사람이 신뢰를 얻는다.

그 거리는 구체적이다. 결제 데모와 실제 예산 위에서 굴릴 수 있는 것 사이의 차이는 이렇다:

PoC / 데모

”결제되네. 출시!”

  • 지갑 하나, 에이전트 하나, 분리 없음
  • 설정만 하고 실제 거부는 테스트 안 한 예산
  • TTL 없음 — 루프가 알아서 끝나길 기대
  • stdout 로깅, 지출-의도 연결 없음
  • kill switch가 “대시보드 볼게요”
  • Bazaar 1만 엔드포인트 전체 접근
Production

”통제하면서, 증명 가능하게 결제한다.”

  • 에이전트별 지갑, hot/cold 분리, 순환
  • 예산 + 누적 한도, 거부가 작동함을 증명하는 테스트
  • 세션 TTL이 시간을 막음 (금액만이 아니라)
  • CloudWatch + X-Ray, 각 지출이 트리거 의도에 연결
  • 훈련된 진짜 kill switch — 그래프 보는 사람이 아니라
  • 머천트 allowlist (Bazaar 전체가 아니라)

오른쪽의 모든 항목은 내가 x402-lab에서 측정했거나 설계로 우회해야 했던 실패에 대응한다. 특별할 것 없다 — “지갑을 연결하라”가 조용히 당신에게 떠넘긴 작업일 뿐이다.

이 통제 질문들을, 같은 실험으로 뒷받침한 체크리스트로 정리했다. 후속 글 **Commerce Agent 거버넌스 프레임워크**를 보라.

맺으며

AWS는 에이전트에게 지갑을 줬고, 그 밑의 프로토콜은 정말로 우아하다. 하지만 “지갑 연결하고 한도 설정”이라는 말은, 부인 불가능한 서명 권한, 초당 3,500건의 지출 속도, 2차원 봉쇄 문제를 한 문장으로 압축한다. 옳은 선택은 두려워하는 게 아니라, 가드를 설계하고 테스트한 뒤에야 결제를 켜는 것이다.

에이전트 경제는 시작됐다. 질문은 “할 수 있는가”가 아니었다. “통제하면서 할 수 있는가”이고, 이건 측정 가능한 답이 있는 엔지니어링 질문이다.
